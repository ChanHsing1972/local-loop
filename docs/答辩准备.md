# LocalLoop 答辩准备

## 先记住这一句话

LocalLoop 是一个自己实现控制循环的编程智能体：模型只负责提出文本或带编号的工具调用，程序负责维护历史、验证并在本地执行工具、把真实结果回填给模型，并在完成、失败或触及边界时停止。

## 30 秒中文开场

“我的项目叫 LocalLoop，是一个不依赖 Agent 框架的交互式编程智能体。它使用兼容 OpenAI 的模型接口，但对话历史、上下文压缩、原生工具调用解析、本地执行、流式展示、重试、会话恢复和终止条件都是自己实现的。它提供目录浏览、文件读取、代码搜索、原子写入和无 Shell 命令五个工具。演示中，模型会先读取代码，再基于真实结果修改并运行测试，终端会逐项显示文件、行号、命令、退出码和输出，而不是只显示抽象步骤。”

## 必须能画出的执行流程

1. 用户输入任务，`interactive.py` 创建或继续一个会话。
2. `agent.py` 把系统提示、用户任务和已有历史交给 `ContextManager`。
3. `provider.py` 以流式 Chat Completions 请求模型。
4. 如果模型返回文本分片，终端立即显示，同时 Provider 在本地拼接完整文本。
5. 如果模型返回 `tool_calls`，Provider 按 `index` 拼接可能被拆开的名称和 JSON 参数。
6. Agent 把完整 Assistant 消息写入 JSONL，再由 `tools.py` 校验参数、路径和权限并执行。
7. 每个结果以包含同一 `tool_call_id` 的 Tool 消息追加到历史，随后再次请求模型。
8. 模型返回非空最终文本时成功结束；超时、调用次数耗尽、重复调用、上下文耗尽、接口错误或用户中断时明确终止。

最核心的不变量是：每个 Assistant 工具调用都必须有且只有一个匹配编号的 Tool 结果。即使工具失败，失败也要作为结构化结果回填，不能把协议链条截断。

## 代码地图

- `agent.py`：核心状态机。它决定何时问模型、何时执行工具、怎样识别连续重复调用、何时停止，并把完整消息写入会话。老师问“agent.py 做什么”，就回答：它是编排层，不负责 HTTP，也不直接读写文件；它把 Provider、Context、Tools 和 Session 串成闭环。
- `provider.py`：传输与解析层。负责普通/流式响应、文本分片、工具参数重组、错误分类、脱敏和有界重试，不负责决定调用哪个工具。
- `tools.py`：五个本地工具及其 JSON Schema、参数验证、工作区边界、审批、原子写入、命令执行和输出截断。
- `context.py`：按“Assistant 工具调用 + 全部 Tool 结果”的完整组压缩旧历史，避免破坏消息协议。
- `session.py`：追加式 JSONL 事件日志、权限收紧、损坏尾行容错和缺失 Tool 结果修复。
- `interactive.py`：Rich/prompt-toolkit 交互界面、输入 `/` 自动展开的命令菜单、连续对话、流式渲染和底部状态栏。命令名称、用法与说明共用一份定义，避免帮助表和补全菜单不一致。
- `config.py`：读取启动目录的 `.env`，再用显式环境变量覆盖；校验工作区、模型和限制。
- `cli.py`：`chat`、`run`、`doctor` 三个入口；`doctor` 验证模型列表、原生函数调用和 Tool 回填闭环。

## 为什么模型以前看起来很慢

旧实现使用非流式请求，必须等一次完整回答生成后才打印，因此“首字可见时间”等于整段生成时间。一个真实编程任务还会经历多轮“模型请求 → 本地工具 → 模型请求”，不能把六次模型调用误认为一次调用卡住。空响应原先最多请求四次，每次又可能等待 60 秒，再叠加 1、2、4 秒退避，最坏等待会被明显放大。现在改成流式显示，最多总共三次请求，并显示每次重试；这主要改善感知速度和故障可见性，模型本身的首 token 延迟仍由模型与网关决定。

## “连续空响应”到底是谁的问题

它不是单一原因。程序按证据区分：认证或权限错误通常是 Key/账号问题；HTTP 429 是限流；408、5xx、连接或读取超时更像网关、上游或网络问题；HTTP 成功但空字符串、空 `choices`，或消息同时没有文本与工具调用，说明网关返回了语义上不可用的数据；工具参数错误、工作区越界或命令退出码非零则是 Agent/任务侧问题。此前截图中的“连续四次空响应”来自 Provider 已经确认收到了空的成功响应后重试，并不代表 `read_file` 失败。现在空响应会有限重试；如果流已经输出一部分后断开，程序不重试，避免重复文字或潜在的重复工具调用。

## 高频问题与推荐回答

### 为什么不直接让模型输出 JSON？

原生工具调用提供明确的工具名、参数边界和调用编号，可可靠关联并行调用及结果。普通文本 JSON 需要从 Markdown 中猜测边界，容易受解释文字、转义和截断影响。项目不做静默降级，`doctor` 会验证目标模型真正支持调用与回填闭环。

### 使用 OpenAI Python 包是否违反“不得使用 Agent SDK”？

不违反。该包只负责 HTTP/SSE 传输和数据对象；它不维护历史、不选择或执行工具、不管理循环、不压缩上下文、不存储会话，也不决定终止。题目明确允许模型厂商 API 客户端和原生 tool calling。

### 流式工具调用怎么解析？

一个工具的 `id`、函数名和参数 JSON 可能分散在多个 SSE chunk 中。Provider 以工具 `index` 为键保存累积状态，逐片拼接字段；流结束后再校验 id 和 name，形成完整 `ToolCall`。正文分片则一边写终端，一边拼入完整 Assistant 消息，保证屏幕显示和会话历史一致。

### 为什么流输出一半断开后不自动重试？

因为已显示内容无法可靠撤回，而且工具参数也可能只收到一部分。盲目重试会出现重复正文，甚至让用户误以为某个操作执行了两次。项目只在尚未收到有效分片时重试；收到分片后断流就诚实失败，由用户恢复或重新提交。

### 为什么命令参数是数组而不是字符串？

数组直接交给 `subprocess.run` 且不启用 Shell，管道、分号和重定向符不会变成额外语法，降低注入风险，也能准确展示待审批命令。代价是复杂 Shell 管道必须拆成多个明确操作。

### SHA-256 写入保护有什么用？

`read_file` 返回整个文件哈希。更新已有文件必须携带该哈希；如果读取后文件被人或其他进程改变，写入会拒绝，模型必须重新读取。这是乐观并发控制，避免静默覆盖新内容。它不能替代版本控制，但能保护 Agent 的“读后写”窗口。

### 为什么写文件采用临时文件加 `os.replace`？

先在同目录写临时文件、刷新并同步，再原子替换目标；进程在写入中途崩溃时，原文件不会只剩半截。更新时还保留原权限。完整文件替换简单可靠，但大文件效率较低，后续可增加补丁工具。

### 上下文为什么不能随便删？

工具协议要求 Assistant 的每个调用后面跟匹配的 Tool 结果。如果只删其中一条，下一次 API 请求可能直接被拒绝。`ContextManager` 把一次 Assistant 调用和后续全部 Tool 结果视为不可拆组，旧组确定性压缩，最近组原样保留；预算仍不够就停止，不发送畸形历史。

### 为什么不用模型总结旧上下文？

确定性压缩不增加调用成本和延迟，不会凭空编造事实，而且输出稳定、易测试；完整历史仍在 JSONL。代价是较早语义会损失，因此这是可解释的工程权衡，而不是最强语义记忆方案。

### 会话崩溃后如何恢复？

每条 JSONL 追加后 flush 并 `fsync`。最后一行若写到一半，加载时只忽略这个尾部残片；如果 Assistant 已记录工具调用但缺少某些结果，则为每个缺失编号追加“执行状态未知”的 Tool 错误。程序不猜测命令是否真的执行过，用户可以先检查现场再继续。

### 安全边界是什么？

路径不能离开工作区，`.env`、Git 内部目录和凭据型文件被阻止；写入和命令默认审批；命令不用 Shell、有超时和输出限制；子进程环境移除 Key/Token/Secret/Password 等变量；明显破坏性命令和改写历史的 Git 子命令被阻止。但这不是操作系统沙箱：获准运行的解释器仍拥有当前用户权限，所以自动批准只能用于可信、可恢复的临时目录。

### `.env` 为什么只从启动目录读取？

这样既满足本地配置，又避免 `localloop -C 陌生仓库` 时自动信任目标仓库提供的配置。显式导出的环境变量优先，`.env` 不会写入会话、提示词或子进程，也被 Git 和 Agent 文件工具双重忽略。

### 循环怎样终止？

成功条件是模型返回非空文本且没有工具调用。保护性条件包括模型调用次数上限、总时长、连续三次相同调用批次、上下文预算失败、输出被截断、接口错误和用户中断。工具失败通常不立即终止，而是回填给模型让其纠正；这是“可恢复错误”和“终局错误”的区别。

### 测试为什么主要使用 FakeProvider？

控制循环必须确定、快速、无费用地覆盖工具调用、错误和边界；真实模型输出不稳定，不适合作为单元测试断言。FakeProvider 验证本地逻辑，真实 API 的 `doctor` 和临时演示项目验证协议兼容与端到端效果，两层测试各自负责不同风险。

### 如果再做一周会加什么？

优先级依次是操作系统/容器沙箱、补丁式编辑与大文件分页、精确 tokenizer、统一结构化事件总线、请求级延迟和 token 指标、任务成功率评测集，而不是先增加更多表面工具。

## 现场答辩策略

回答时先说结论，再指向具体模块和不变量，最后主动承认边界。例如：“不会自动重复执行，因为收到流分片后立即失败；这个判断在 Provider，原因是避免重复文本和副作用；但进程级 exactly-once 仍无法保证，所以恢复时把未完成工具标为状态未知。”如果演示遇到接口异常，先运行 `localloop doctor`，说明本地测试与真实网关测试的分层，不要为了显得成功而把失败归因成一句“网络不好”。
