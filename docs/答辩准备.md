# LocalLoop 答辩准备

## 1. 30 秒开场

“LocalLoop 是一个不依赖 Agent 框架的交互式编程智能体。模型只能返回文本或带编号的工具调用；程序自己维护历史和上下文，在本机验证并执行目录、读取、搜索、写入和命令五个工具，把真实结果交还模型，并在完成、失败或触及边界时停止。我把 Provider、Agent、Tools、Context 和 Session 分层，因此每个关键状态都可以测试、恢复和解释。”

## 2. 必须能画出的图

```text
用户
  -> InteractiveShell
  -> AgentEngine -> ContextManager -> OpenAIChatProvider -> 模型
                    ^                                  |
                    |                                  v
                 SessionStore <- ToolResult <- LocalTools
```

讲图时强调：模型只提出动作；Agent 决定流程；Tools 掌握本地执行；Session 保存证据。每个 Assistant tool call 必须有一个同编号 Tool 结果，这是协议不变量。

## 3. 模块一句话职责

- `types.py`：定义跨层传递的数据和协议。
- `config.py`：合并启动目录 `.env` 与环境变量，并校验配置。
- `cli.py`：组织默认交互、`run` 和 `doctor` 三个入口。
- `interactive.py`：持续输入、斜杠命令、菜单、流式呈现和状态栏。
- `agent.py`：有界模型-工具循环和所有终止分支。
- `provider.py`：普通/流式接口传输、响应解析、脱敏和重试。
- `tools.py`：工具 Schema、参数与路径验证、审批和本地执行。
- `context.py`：不破坏工具消息协议的确定性历史压缩。
- `session.py`：仅追加 JSONL、权限、恢复和单会话删除。

## 4. 高频问题与基于代码的回答

### 为什么可以使用 OpenAI Python 包？

题目允许模型厂商客户端和原生 tool calling。该包只负责传输；它没有替我维护历史、选择工具、执行工具、压缩上下文或决定终止，关键 Agent 逻辑都在本地模块中。

### 为什么不用模型输出普通 JSON？

原生 tool calling 有明确的工具名、参数边界和调用编号，能处理一轮多个调用并准确关联结果。普通文本 JSON 容易混入解释、Markdown、转义或截断，解析边界不可靠。

### Agent 为什么不在工具成功后立刻结束？

工具成功只是一个事实，还需要模型读取结果并判断任务是否完成。成功条件是模型返回非空最终文本且没有新工具调用；命令退出码 0 不能替代模型的最终总结。

### 为什么失败结果也要回填？

模型需要看到越界、参数错误、命令失败或写入冲突才能修正下一步。更重要的是，丢掉失败结果会破坏 Assistant tool call 与 Tool 消息的协议配对。

### 流式工具调用怎样解析？

同一调用的 id、函数名和参数 JSON 可能分散在多个 SSE chunk。Provider 以 `index` 为键累积字符串，流结束后校验并创建完整 `ToolCall`；正文则边显示边保存，保证屏幕和历史一致。

### 为什么显示过正文后断流不重试？

已经显示的文字无法可靠撤回，工具参数也可能只到一半。自动重试会重复正文，甚至模糊副作用是否发生。未收到有效分片时可以有限重试；收到后中断就明确失败。

### SHA-256 有什么作用？

`read_file` 返回整个文件哈希。写已有文件必须提供该哈希；若读后文件被用户或别的进程改变，写入拒绝。这是乐观并发控制，避免静默覆盖，不是版本控制替代品。

### 为什么要临时文件加 `os.replace`？

先完整写入同目录临时文件并同步，再原子替换目标。进程在中途崩溃时，原文件不会只剩半截；更新还保留旧权限。代价是要发送完整文件内容。

### 为什么命令是数组？

数组直接传给 `subprocess.run` 且不启用 Shell，分号、管道和重定向没有额外语法意义，审批时也能准确展示 argv。复杂 Shell 流水线必须拆成明确步骤。

### 上下文为什么按组压缩？

Assistant 工具调用和后续 Tool 结果是一个协议单元，只删其中一条会让网关拒绝请求。ContextManager 保留前两条和最近交互，把较早完整组压缩成确定性预览；完整原始记录仍在 JSONL。

### 为什么不用另一个模型总结历史？

确定性压缩没有额外延迟和费用，不会编造事实，结果稳定可测。代价是旧语义损失更多，因此文档把它作为明确权衡而不是完美记忆。

### 崩溃后怎样恢复？

JSONL 每次追加后 flush 和 `fsync`。只忽略最后一条未完成 JSON；若 Assistant 调用已写入但 Tool 结果缺失，就为缺失编号追加“状态未知”。程序不会猜测或自动重做可能已有副作用的动作。

### `/new` 和 `/delete` 有什么区别？

`/new` 只放下当前内存上下文，磁盘日志仍可 `/resume`；`/delete ID` 在确认后删除指定 JSONL。如果删除的是当前会话，内存上下文同时清空。

### 安全边界是什么？

程序限制工作区路径和敏感文件，写入/命令默认审批，命令无 Shell、有超时和输出上限，子进程环境移除秘密变量，并阻止明显破坏性命令。但获准的解释器仍有当前用户权限，所以这只是防误操作层，不是沙箱。

### 测试为什么大多使用 FakeProvider？

控制循环的边界必须快速、确定、免费地重复验证。FakeProvider 证明本地状态机；临时 Git 集成测试证明真实文件与子进程闭环；`doctor` 证明真实网关协议；真实演示证明模型在一个任务上的实际体验。四者不能互相冒充。

## 5. 如何评价真实对话记录

判断 Agent 是否“正常”至少看五项：是否先读后写；修改是否与题意一致；是否用真实命令验证；工具失败后是否能基于错误调整；最终总结是否与工具证据一致。界面质量再看等待提示是否简短、工具输出是否保留结构、失败原因是否真实、临时产物是否处理、长行是否易读。

不能只因为最后显示“已完成”就判定成功。若测试只做语法检查、命令失败被写成“未知错误”、清理被阻止后留下产物，均应在评价中如实说明。

## 6. 如果再做一周

优先级应是：容器/操作系统沙箱；补丁式编辑和受控删除工具；精确 tokenizer；结构化事件总线与延迟/token 指标；固定任务评测集；再考虑新增表面功能。这个顺序体现对安全、证据和可维护性的重视。

## 7. 回答策略

先给结论，再指出模块和不变量，最后承认限制。例如：“不会在已显示正文后自动重试；判断在 Provider；原因是避免重复文字和副作用；但进程级 exactly-once 仍无法保证，所以恢复时把缺失结果标记为状态未知。”不要用“网络不好”“框架帮我做了”或“测试都过了所以肯定安全”这类无法辩护的说法。
